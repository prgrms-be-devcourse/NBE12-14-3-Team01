## 2. 공통 오류 대응 (제안)

409를 하나의 알림창으로 처리하지 않는다. HTTP 상태로 큰 분류를 하고, **code로 화면별 행동**을 정한다 ([G03-D-03](../decisions/proposals/G03-D-03-error-code.md) §5-3). code 번호는 S2-4에서 정한다.

| 종류 | 사용자에게 | 다음 행동 | 자동 재시도 |
|---|---|---|---|
| CONFIRM_REQUIRED (409) | 충돌 목록 (근무, 대상, 겹치는 시간) + 확인 체크 | 확인하면 **같은 요청 + 확인한 목록**으로 다시 보냄. 오류 화면이 아니라 확인 화면 | 없음 |
| STALE (409) | "근무 또는 구성원 상태가 바뀌었습니다. 다시 확인해 주세요". **의미: 제출한 계획이 지금 상태와 맞지 않아 다시 조회해야 한다** (미리보기 이후에 바뀌었다는 것을 서버가 증명한다는 뜻은 아님) | 미리보기·목록과 비교 정보(previewContext 후보)를 **다시 조회**한다. 여전히 유효한 선택만 복구하고 추가/변경 영향을 다시 보여 준다. 이전 충돌 확인은 폐기 | 없음 |
| STATE_CONFLICT (409) | 상태 안내 (예: "이미 퇴사한 직원입니다", "진행 중인 근무가 18:00에 끝납니다") | 안내만. 필요하면 화면 새로 고침 | 없음 |
| FORBIDDEN_CONFLICT (409) | "다른 공식 근무와 겹칩니다" | 다른 직원이나 시간 선택. **확인으로 넘어갈 수 없음** | 없음 |
| DUPLICATE (409) | "이미 참여 중인 근무지입니다" 등 | 중단 | 없음 |
| 404 | "찾을 수 없거나 접근할 수 없습니다" **한 가지 문구** (없음과 권한 없음을 구별하지 않음) | 목록으로 돌아감 | 없음 |
| 403 `WPL-003` (현재 구성원 아님) | "이 근무지에 더 이상 소속되어 있지 않습니다" | **근무지 목록으로 이동** (§6) | 없음 |
| 403 그 밖 | 서버 문구 | 안내 | 없음 |
| 503 (실험 후 적용) | "잠시 후 다시 시도해 주세요" | 최신 상태를 다시 조회한 뒤 **사용자가 직접** 다시 시도. 변경 요청을 자동으로 다시 보내지 않음 (결과가 Commit됐는지 모를 수 있음) | 없음 |
| 401 | 기존 그대로 (`AUTH-006`이면 1회 재발급, 그 밖은 로그인 화면) | — | `AUTH-006`만 1회 |

**기존 화면은 그대로:** DRAFT 근무·Publish·불가능 시간 등록의 `window.confirm` 흐름은 기존 API 형식이 유지되므로 바꾸지 않는다 ([G03-D-05](../decisions/proposals/G03-D-05-confirmation-response.md) D05-8). 새 화면에만 위 규칙을 쓴다.

**알림 읽음 실패 복구 (S3-A, 사용자 잠정 결정 2026-10-25, 팀 `PENDING`, USER-PATH-REVIEW G-1):** 지금은 모든 실패에 "다시 시도해주세요"만 띄우고 목록을 다시 받지 않는다 (`AppHeader` L263-268). HTTP 상태로 나눈다.

| 실패 | 사용자에게 | 목록 |
|---|---|---|
| 403 / 404 (권한 상실·없음, 예: 퇴사한 소속의 알림) | "이 알림은 더 이상 볼 수 없습니다" | **현재 소속 기준으로 다시 조회** (그 항목이 사라짐) |
| 네트워크 오류·5xx | "읽음 처리하지 못했습니다. 다시 시도해 주세요" | 그대로 유지 (일시 실패와 권한 상실을 섞지 않음) |
| 401 | 기존 처리 | — |

`NOT-001`·`NOT-002` 중 무엇이 오는지(G03-D-10, `DEFER`)와 관계없이 HTTP 상태로만 분기한다.

### 3-4. 끝난 대타 요청 (관리자, S3-A, 사용자 잠정 결정 2026-10-25, 팀 `PENDING`)

| 항목 | 내용 |
|---|---|
| 위치 | 승인 관리 화면(`substitutes/admin`)의 "끝난 요청" 탭. 기존 진행 중 목록은 그대로 |
| API | API-SB-02 `GET /api/v1/workplaces/{workplaceId}/substitute-requests/closed?from=&to=&page=&size=` (기본 최근 7일, `from`·`to`는 ISO 날짜시각 예 `2026-10-22T10:00:00`, `page` 0부터, `size` 기본 20·최대 100). 응답 `data = { items, page, size, hasNext }`. 결과는 `outcome`(`CLOSED`·`EXPIRED`) + `closeReason`(만료는 `EXPIRED`). "조치 필요"의 전원 거절·후보 자격 상실 = `outcome = CLOSED` ∧ `closeReason ∈ {ALL_CANDIDATES_REJECTED, CANDIDATE_INELIGIBLE}` (2026-10-29 구현, 팀 승인은 PR 리뷰로 요청 중) |
| 행 표시 | 근무 날짜·시간, 요청자 (`requesterMembershipEnded`면 "(이전 소속)" — 재가입한 사람도 그 요청의 소속은 끝났으므로 "퇴사"로 단정하지 않음), 결과 문구 (전원 거절 / 후보 자격 상실 / 근무 변경으로 종료 / 관리자 종료 / 승인 전에 근무 시작), 종료 시각, 수락자 (있었으면) |
| **조치 필요** 표시 | `outcome`이 전원 거절·후보 자격 상실이고 **근무 상태 `SCHEDULED`** ∧ `requesterStillAssigned` ∧ ¬`shiftStarted` ∧ ¬`hasNewerActiveRequest` → "조치 필요" + 담당자 변경(API-PS-03) 바로가기. 취소된 근무·시작한 근무에는 표시하지 않는다 (S3-B). 문구는 "다른 직원 배정을 검토하세요"이며 새 대타 요청이 필요하다는 뜻이 아니다 |
| **확인 필요** 표시 | `outcome = EXPIRED`이고 수락자가 있었음 → "승인 전에 근무가 시작됨 — 실제 근무자를 확인하세요" (시스템 안 조치 없음, 안내만) |
| 규칙의 위치 | 위 표시 규칙은 이 문서가 원본이다. API는 판단하지 않고 사실 Field만 준다 (API-CATALOG API-SB-02). 표시는 안내일 뿐이며, 바로가기로 실행한 Command(담당자 변경 등)가 가능한지는 **서버가 그 시점에 다시 검증**한다 (목록을 본 뒤 상태가 바뀔 수 있음) |
| 하지 않는 것 | 행에서 바로 승인·종료 (끝난 요청), 거절 후보 표시, 퇴사자 프로필로 이동 |
| 구현 (2026-10-29, V4 Owner) | 승인 관리 화면 세 번째 탭 "끝난 요청" (`substitutes/admin/page.tsx`). API-SB-02를 따로 불러 실패해도 다른 탭은 그대로, `hasNext`면 "더 보기". 결과 배지: 전원 거절·후보 자격 상실(빨강) / 근무 변경으로 종료·관리자 종료·승인 전에 근무 시작(회색), 아래 줄 "MM.DD (요일) HH:mm 종료"(만료는 "만료 시각 …"). 조치 필요·확인 필요는 위 조건 그대로. 조치 필요 바로가기는 근무표 화면(`/workplaces/{id}/schedule`)으로 이동 (담당자 변경 화면이 근무표에 있음, 해당 주를 지정해 여는 것은 후속). 종료 Command 성공 시 끝난 요청 목록을 다시 불러옴 |

## 7. 승인 이력과 현재 담당 표시

| 사실 | 어디서 보이나 | 데이터 출처 |
|---|---|---|
| "이 대타 요청이 승인되었다" (과거 사실) | 보낸 요청(요청자), 수락한 요청 — 종료(수락자) | Request(APPROVED) + Candidate(ACCEPTED). 현재 `Shift.member`를 읽지 않음 |
| "지금 이 근무의 담당은 나다" | 예정 근무 | 현재 `Shift.member` = 나의 현재 소속 |
| "이 근무가 나에게서 빠졌다" | 빠진 근무 | Shift 취소 정보, 배정 이력 (당시 소속 ID) |

예: A의 근무를 B가 대타로 승인받은 뒤 관리자가 C에게 인계하면
- A: 보낸 요청에 "승인됨" (그대로)
- B: 수락한 요청 — 종료에 "승인됨 — 현재 근무는 예정 근무에서 확인하세요", 빠진 근무에 "다른 직원에게 인계됨", 예정 근무에서는 사라짐
- C: 예정 근무에 나타남

"승인됨" 문구는 현재 담당을 단정하지 않는다.

## 9. S2-3C 결정 (사용자 잠정 결정 2026-10-25, 팀 승인 전)

### 9-1. 같은 근무지의 인계 대상이 확정 전에 현재 소속이 아니게 된 경우 → 409 STALE

| 상황 | 응답 | 화면 |
|---|---|---|
| 인계 대상이 같은 근무지의 소속이지만 지금은 현재 소속이 아님 | **409 STALE** — 그 계획으로는 확정할 수 없음 | 미리보기를 다시 조회하고 인계 대상을 다시 고르게 함 |
| 퇴사 대상 자체가 이미 종료된 소속 | 409 STATE_CONFLICT — 그 업무를 다시 실행할 수 없음 | "이미 퇴사 처리된 직원입니다" 안내 |
| 인계 대상·퇴사 대상 ID가 없거나 다른 근무지 소속 | 404 — 존재를 드러내지 않음 | "찾을 수 없거나 접근할 수 없습니다" |

STALE은 "제출한 계획이 지금 상태와 맞지 않아 다시 조회해야 한다"는 뜻이다. 서버가 "미리보기 이후에 퇴사했다"는 것을 증명한다는 뜻이 아니다.

### 9-2. 빠진 근무에 새 담당자 이름을 보여 주지 않음

- 직원의 빠진 근무에는 "다른 직원에게 인계됨"과 근무 시간·사건 시각만 보여 준다.
- **API 응답에도 새 담당자의 이름·ID를 넣지 않는다** (화면에서만 숨기지 않음).
- 관리자는 근무표 관리 화면에서 현재 담당자를 본다 (기존 그대로).

### 9-3. 이전 소속 데이터가 화면에 남는 위험 (교차 검토 의견, 정적 확인)

- 권한의 기준은 **서버의 현재 소속 조건**이다 (API-CATALOG CHG-02·03·04). 화면의 `workplaceId` 필터는 화면 정리용 보조 수단이지 권한 보장이 아니다.
- 지금 Frontend는 공용 Cache가 없고 화면을 열 때마다 다시 조회하므로(§1), 남는 위험은 **퇴사·재가입·로그아웃 순간에 이미 열려 있던 화면**에 이전 목록이 남아 있는 경우로 한정된다.
- 대응 (제안): ① 퇴사 확정·가입·로그아웃 뒤에는 화면 이동과 다시 조회를 함께 한다. ② 어떤 요청이든 403 `WPL-003`을 받으면 그 근무지 화면의 상태를 버리고 근무지 목록으로 이동한다 (§6). ③ 공용 Cache를 나중에 도입하면 근무지 단위가 아니라 로그인 세션과 소속 변경 시점에 비우도록 설계한다.
- 화면은 소속 ID를 모르므로(§1) 재가입 전후를 스스로 구별할 수 없다. 그래서 위 ①②로 충분하고, 응답에 소속 ID를 추가하는 것은 필요하지 않다 (추가하면 기존 API 응답 변경, 승인 대상).
- **원칙:** 소속·인증 상태가 바뀐 것을 화면이 알게 된 시점(퇴사 확정 성공, 가입 성공, 로그아웃, 403 `WPL-003`, 401)에는 그 근무지의 업무 데이터를 버리고 새 서버 응답으로 다시 그린다. 그 시점 전에 보낸 요청의 응답이 늦게 도착하면 반영하지 않는다 (지금 `apiFetch`의 `sessionVersion`이 로그인·로그아웃에 대해 같은 방식을 쓴다, `lib/api.ts` L66-145. 소속 변경에도 같은 방식을 쓸지는 Frontend 구현 때 정한다).
- **한계:** 서버가 퇴사 사실을 브라우저에 실시간으로 알리는 기능이 없다. 그래서 **다른 브라우저·탭에 이미 열려 있는 화면의 이전 데이터를 즉시 지운다고 보장할 수 없다.** 그 화면은 다음 요청에서 서버의 현재 소속 조건으로 막히거나 다음 조회에서 사라진다. 실시간 반영은 이번 범위 밖이다.
- **오류별 해석을 섞지 않는다:** 403 `WPL-003`(이 근무지의 현재 구성원이 아님)만 "소속을 잃었다"로 해석해 근무지 화면을 초기화한다. **404(범위 밖 ID)는 "그 항목을 찾을 수 없거나 접근할 수 없다"일 뿐 소속 종료를 뜻하지 않는다** (존재 노출을 막으려고 여러 경우를 하나로 합친 응답이므로). 409 STALE은 그 목록·미리보기만 다시 조회한다. 401은 인증 처리 (§2).

### 퇴사 미리보기의 1차 확정 흐름 (2026-10-26)

미리보기 표시값과 비교 정보를 같은 응답에서 보관한다. 확정할 때 비교 정보와 관리자가 선택한 decisions를 함께 보내고, 임의로 자동 정리 대상을 수정해 보내지 않는다. 서버가 대상과 권한을 결정한다.

미리보기 D1/D2 → 현재 D1이면 다른 조건 통과 후 진행 가능하다. 현재 D1/D3 또는 D1/D2/D3면 STALE이다. 대타 후보의 상태 변경으로 정리 영향이 커져도 STALE이다. 응답은 오류 후 자동 재확정을 하지 않고 새 미리보기를 보여 준다. CONFIRM_REQUIRED에는 기존 비교 정보를 유지해 확인 목록을 더하고, STALE에는 비교 정보와 확인 목록을 함께 교체한다. 성공 후 화면/알림이 일부 늦어도 서버 결과 조회로 확인한다. 중복 클릭 방지 UI만으로 중복 처리 방지를 보장하지 않으며 서버도 재검증한다.
