## 1. 왜 지금 정해야 하나

- 불가능 시간은 직원이 "이 시간에는 일할 수 없다"고 등록한 시간이다. 근무지가 아니라 User 전역 Resource다 (G03-C-33).
- 현재 Java는 기능마다 처리 방식이 다르다: 관리자 배정은 경고 후 확인, 대타 수락·승인은 거부, 후보 선정은 제외.
- 이 차이가 의도인지 결정되지 않았다 (G03-D-21 `PENDING`). 2차 명세끼리도 다르다: API-SUB는 수락·승인 "차단", P0 가이드 §16은 "경고".
- 퇴사 인계와 공개 후 담당자 변경이 새로 생기면, 같은 사람에게 같은 근무를 주는 경로가 둘(대타 승인, 관리자 직접 배정)이 된다. 두 경로의 규칙과 기록이 정해지지 않으면 "승인은 막혔는데 직접 배정으로 우회"한 결과를 구분할 수 없다.

### 4-1. 명세 불일치의 처리

- API-SUB(수락·승인 차단)와 Java가 같고, P0 가이드 §16("경고")이 다르다. 이 카드는 API-SUB와 Java를 따른다.
- 원문(외부 명세)은 수정하지 않는다. 이 카드와 `DECISION-LOG`가 후속 결정으로 설명한다. 명세 문장 수정 여부는 팀 확인 사항이다.

## 7. API·Frontend 영향

### 7-1. 바뀌지 않는 것 (Migration 보존)

DRAFT 생성·수정과 Publish의 `confirmUnavailableConflict`, 수락·승인의 `SUB-006`, 후보 제외, 불가능 시간 등록의 `OFFICIAL_SHIFT_CONFLICT` 확인 Flow. Kotlin Migration은 그대로 옮긴다.

### 7-2. 알려진 한계 (AS-IS, 이번에 바꾸지 않음)

- Publish는 확인 Flag가 `boolean` 1개다. 관리자가 경고를 보고 확인한 뒤 다시 보내기 전에 다른 직원의 새 충돌이 생기면, 그 새 충돌도 같은 확인으로 통과한다. D21-8이 막으려는 위험이 기존 Publish에도 있다는 뜻이다. 이번에는 새 Command에만 목록 확인을 적용하고, Publish는 현재 동작을 유지한다 (후속 후보).
- **(2026-10-25 재평가, 확인 범위 관점)** Publish의 409 응답은 `ConfirmationRequiredResponse(true)`뿐이라 **어느 근무·직원이 충돌하는지 알려 주지 않는다** (`ScheduleService` L504-520). 화면은 `window.confirm`으로 일반 문구만 보여 준다 (`schedule/page.tsx` L627-650). 따라서 관리자의 확인은 시간 경합과 무관하게 이미 "내용을 모르는 모든 충돌"에 대한 동의다. 이것은 D21-1의 "충돌 사실을 관리자에게 명확히 알림"을 **Publish에서는 충족하지 못한다**는 뜻이다 (DRAFT 생성·수정은 근무 1건이라 문구만으로도 대상이 분명하다). 불변식(공식 근무 중복 금지 등)은 깨지지 않고 현재 2차 서비스와 같은 동작이므로 Migration은 그대로 옮긴다. 개선 등급은 **P1 최우선 후보**로 두고, 팀이 P0로 올릴지 판단한다. 새 Command(D21-7·8)가 P0에서 만드는 "충돌 목록 + 확정 시 재계산" 방식을 Publish에도 적용하는 것을 추천한다. 새 Command는 이 `boolean` 방식을 복사하지 않는다.
- DRAFT 생성·수정은 대상 User Lock을 잡지 않는다. 동시에 불가능 시간이 등록되면 확인 없이 겹치는 DRAFT가 남을 수 있다. 공개할 때 Publish가 User Lock 이후 다시 검사하므로 공식 근무로는 이어지지 않는다 (정적 추론, 실행 확인 없음).

### 7-3. 새 Command (ML-2·ML-4에서 정의, 여기서는 원칙만)

- 공개 후 추가·담당자 변경: 한 근무에 대한 경고 후 확인. 확인 Flag 방식은 기존 DRAFT와 같게 할지 ML-2에서 정한다.
- 퇴사 확정: 요청에 "확인한 불가능 시간 충돌 목록"(근무 ID·대상 소속)을 담는다. 서버는 다시 계산한 목록과 비교한다. 형식(목록 자체 vs Hash)은 ML-4에서 정한다.
- ErrorCode: 새 Command의 충돌 경고 code와 "확인 목록 불일치" 409 code는 G03-D-03에서 정한다. 기존 `SFT-015`를 재사용할지도 그때 정한다.

### 7-4. Frontend

- 퇴사 미리보기: 근무별 인계 대상과 함께 불가능 시간 충돌 근무·직원·구간을 표시하고, 한 번 확인받는다.
- 409 "확인 목록 불일치"를 받으면 새 미리보기를 다시 보여 준다.
- 직원 화면에 불가능 시간 등록 시 "기존 근무는 그대로 유지됩니다" 안내를 넣을지는 Frontend 담당 판단 (선택).

## 8. 동시성 (ML-5로 넘기는 검증 항목, 실험 전)

현재 확인한 사실: 불가능 시간 쓰기 3종, 대타 수락, 대타 승인, Publish는 모두 해당 User `FOR UPDATE`를 잡은 뒤 검사한다 (§2). 그래서 이들 사이는 User Row로 직렬화된다고 **추론**한다. 실행으로 확인하지 않았다.

| ID | 경합 | 확인할 것 |
|---|---|---|
| D21-R1 | 퇴사 확인 시점에는 충돌 없음 → 확정 전에 대상 직원이 불가능 시간 등록 | 확정이 새 충돌을 찾아 409 (D21-8). 퇴사 확정이 인계 대상 User Lock 이후 검사하는지 |
| D21-R2 | 퇴사 확인 시점에는 충돌 있음 → 확정 전에 직원이 불가능 시간 삭제 | 최종 상태 모순 없음. 409 또는 진행 중 어느 쪽인지 ML-4 결정대로 |
| D21-R3 | 직원의 불가능 시간 등록 vs 같은 직원의 대타 수락 동시 실행 | 최종 상태가 "겹치는 수락" 또는 "확인 없는 겹치는 불가능 시간" 중 하나로 남지 않음 (User Lock 직렬화 확인) |
| D21-R4 | 불가능 시간 등록 vs 관리자 공개 후 담당자 변경 (같은 직원) | 담당자 변경이 대상 User Lock 이후 검사하는지 (ML-5 표 "사람에게 근무를 주는 일 = User Lock") |
| D21-R5 | DRAFT 생성 vs 불가능 시간 등록 (§7-2) | AS-IS 재현 여부만 기록. Publish 재검사로 공식 근무에는 이어지지 않는지 |

로컬 ML-5 Draft에는 불가능 시간 쓰기가 Lock 표에 없다. S2에서 ML-5를 옮길 때 이 표를 연결한다.

## 10. 재검토 조건

- 대타 승인에서 관리자 확인 후 진행이 필요하다는 운영 요구가 생기면 D21-3을 다시 연다.
- Publish 확인 방식을 목록 확인으로 바꿀 필요가 생기면 §7-2를 별도 Improvement로 연다.
- ML-5 실험(D21-R1~R5)에서 직렬화가 성립하지 않으면 D21-8의 보장 수단을 다시 정한다.
