## 1. 왜 지금 정해야 하나

- G03-D-21에서 "관리자 직접 배정은 불가능 시간 경고 후 확인, 여러 근무를 한 번에 배정할 때는 충돌 목록을 한 번 확인하고 확정 때 다시 계산"으로 정했다 (D21-7·8).
- 지금 경고 응답은 "확인이 필요하다"는 `boolean` 하나뿐이라 **어느 근무·직원이 충돌하는지 담을 수 없다.**
- 퇴사 확정(ML-4)과 공개 후 담당자 변경(ML-2)의 API 계약이 이 형식에 달려 있다.

## 3. 핵심 사실: 충돌은 관리자가 고른 인계 대상에 따라 정해진다

퇴사 미리보기(ML-4 §6)는 퇴사자의 근무 목록을 보여 줄 뿐이고, 인계 대상은 관리자가 그 화면에서 고른다. 그래서 **미리보기 응답에는 충돌 목록을 넣을 수 없다.** 충돌은 확정 요청(결정이 담긴 요청)을 받았을 때 처음 계산할 수 있다.

### 4-2. 계획 유효성 검사 (D05-3 ②)

확정 시 서버가 Lock 후 다시 읽고 **관리자가 확인한 미리보기**와 비교한다(2026-10-26 사용자 선택). 결정 대상의 ID·담당·상태·시간이 바뀌면 STALE이다. 자동 대상은 대상+처리 효과를 비교해 기존 효과만 감소하면 진행 가능하며, 새 대상·효과 확대·같은 건수의 대상 교체는 STALE이다. 다른 필수 조건도 모두 통과해야 한다. 이번 요청의 실패 시 업무 변경0을 보장한다.

| # | 확인 | 다를 때 | 이유 |
|---|---|---|---|
| P1 | 퇴사자의 미래 공식 근무 ID 집합 = 요청 `decisions`의 근무 ID 집합 | STALE | 관리자가 결정하지 않은 근무가 생기거나 사라짐 (ML-4 §6) |
| P2 | 각 근무: 현재 담당 = 퇴사자, SCHEDULED, 시작 전, **시작·종료 시각이 미리보기 값과 같음** | STALE | ID가 같아도 근무가 바뀌었을 수 있다. 지금은 공개 근무 시간 변경 경로가 없지만(D-27 시간 변경 보류) 확장에 대비 |
| P3 | 각 인계 대상: 같은 근무지의 현재 소속 (Lock 후 다시 읽음) | STALE | 그 사이 대상이 퇴사했을 수 있다 (ML-5 Guard) |
| P4 | 퇴사자: 현재 소속, 진행 중 근무 없음 | 409 STATE_CONFLICT | ML-4 규칙 (이미 퇴사·진행 중 근무) |
| P5 | DRAFT·대타 영향(자동 처리 대상). **P1~P4를 모두 통과한 뒤에만** 판단한다 | **줄어들면 진행(남은 대상으로 처리), 새로 생기면 STALE** | 미리보기에서 확인하지 않은 대상/효과를 조용히 처리하지 않는다. 별도로 Lock 대기 중 새 Row도 재검사한다. 새 Row를 순서 밖으로 추가 잠금하면 교착 후보가 될 수 있다 (ML-5, 원문 ML-CONCURRENCY-01-R §4 "Σ1 ⊄ Σ0이면 중단"). 사라진 Row는 처리하지 않으면 된다 |

P2의 "미리보기 값"은 요청에 근무별 시작·종료 시각을 함께 보내 비교하는 방식을 후보로 둔다 (S2-3B에서 Field 확정).

확인 목록과 무관하게 거부한다 (G03-D-21 D21-5): 인계 대상의 공식 근무 중복, 권한 없음, 다른 근무지 소속, 시작한 근무.

## 5. 응답·요청 형식 (후보, Field 이름은 S2-3B에서 확정)

### 5-1. 모양

```
409 CONFIRM_REQUIRED
data: {
  requiresConfirmation: true,
  unavailableConflicts: [
    { shiftId, shiftStartAt, shiftEndAt,
      targetMemberId, targetName,
      overlaps: [ { startAt, endAt } ] }    ← 근무 시간 안의 겹침 구간만 (S05-a)
  ]
}

확정 요청
{
  decisions: [ ... ],
  acknowledgedUnavailableConflicts: [
    { shiftId, targetMemberId, overlaps: [ { startAt, endAt } ] }
  ]
}
```

- 기존 `ConfirmationRequiredResponse`에 Field를 **더한** 모양이다. 새 Command에서만 쓰므로 기존 계약은 바뀌지 않는다.
- 공개 후 담당자 변경은 기존 `shiftId` 형식(목록 1건)을 쓴다. **신규 추가는 아직 Shift ID가 없으므로 아래 `newShiftKey` 형식으로 구분한다.**
- 신규 공개 근무 추가의 충돌 응답/확인 항목은 `shiftId`를 요구하지 않는다. 대신 `newShiftKey: { scheduleId, targetMemberId, shiftStartAt, shiftEndAt }`와 `overlaps`를 사용한다. `scheduleId`는 Path의 근무표, `targetMemberId`는 요청의 현재 소속 `memberId`, 시각은 요청의 `startAt/endAt`과 같아야 한다. 서버가 정규화한 같은 시각 정밀도로 비교한다. 네 값이 모두 같은 계획에 대해서만 확인 범위를 재사용한다.
- 서버는 Path·요청의 현재 계획을 기준으로 권한·소속·근무표·시간·공식 근무 중복을 다시 검사한다. `newShiftKey`는 클라이언트가 보낸 확인 범위의 대응 키이며 DB 사실이나 변조 불가능한 동의 증거가 아니다(D05-5).
- 신규 추가의 첫409에서는 Shift·배정 이력·알림을 저장하지 않는다. 같은 계획의 확인 재요청이 모든 검사를 통과한 때만 생성한다. 대상/근무표/시각을 바꾸면 다른 키이므로 이전 확인 항목으로 통과하지 않는다. 이 키는 중복 제출을 성공 응답으로 재생하는 멱등성 키가 아니며, 응답 유실 시 자동 재시도 금지(D05-7)는 유지한다.
- `targetMemberId`는 **인계 대상의 현재 WorkplaceMember ID**다 (User ID가 아님). 재가입한 사람의 이전 소속과 섞이지 않는다.

### 5-2. 충돌 응답에 보여 줄 범위 (S05-a, 사용자 잠정 결정 2026-10-25: (가))

**근무 시간 안에서 실제로 겹치는 구간만** 보여 준다.

| 응답에 넣는 것 | 응답에 넣지 않는 것 |
|---|---|
| 근무 ID, 근무 시작·종료, 인계 대상 (현재 소속 ID, 이름), 근무 시간 안의 겹침 구간 | 불가능 시간의 원래 시작·종료, 불가능 시간 ID(`unavailableTimeId`), 등록 사유·메모, 다른 근무지 정보, 겹침 구간을 만든 불가능 시간이 몇 건인지 |

- **화면에서 숨기는 것이 아니라 API 응답에서 뺀다.** 브라우저에 전달된 값은 관리자가 볼 수 있다고 본다.
- `unavailableTimeId`는 빼도 된다. 서버의 비교는 겹침 구간으로 하고(§5-3), 동시성은 User Lock으로 한다(§7). 관리자에게 필요한 값이 아니다.
- 충돌 상세는 **권한 있는 현재 관리자가 보낸 유효한 계획**(D05-3 ①~③ 통과)에 대해서만 돌려준다. 그래도 관리자가 여러 시간대로 반복 시도하면 가능 여부를 간접적으로 추정할 수 있다는 한계는 남는다. 시도 횟수 제한은 이번 범위 밖이다.

| 선택지 (기록) | 판단 |
|---|---|
| (가) 겹침 구간만 | **선택.** 판단에 필요한 정보만 드러남. 지금 관리자는 직원의 불가능 시간을 볼 경로가 없다(§2)는 현재 권한과 맞음 |
| (나) 불가능 시간 전체 | 근무 밖 개인 일정까지 노출 |
| (다) 겹침 여부만 | 판단 정보 부족 |

### 5-3. 겹침 구간 비교 규칙

관리자가 확인하는 대상은 "특정 불가능 시간 Row"가 아니라 **"이 근무를 이 사람에게 줄 때 근무 시간 중 겹치는 시간"**이다. 그래서 비교도 Row가 아니라 시간으로 한다.

1. **정규화:** 같은 (근무, 인계 대상)에 대해 겹치는 불가능 시간을 모두 근무 시간 `[shiftStartAt, shiftEndAt)` 안으로 자른 뒤, 겹치거나 맞닿은 구간을 합쳐 서로 떨어진 구간 목록으로 만든다 (`[18:00,19:00)`과 `[19:00,20:00)` → `[18:00,20:00)`). 응답의 `overlaps`는 이 정규화된 목록이다.
2. **비교:** (근무, 인계 대상)마다 **현재 겹침 구간이 확인한 겹침 구간에 시간으로 모두 포함되면** 그 쌍은 통과다. 확인 목록에 없는 (근무, 인계 대상) 쌍에 겹침이 있으면 통과하지 못한다.
3. 하나라도 통과하지 못하면 409 CONFIRM_REQUIRED + 최신 정규화 목록.
4. 인계 대상·근무 자체·근무 시각이 바뀐 경우는 이 비교 전에 계획 유효성(§4-2 P1~P3)에서 STALE로 끝난다. 충돌 목록이 같아 보여도 마찬가지다.
5. 시각 비교는 같은 `Clock`(Asia/Seoul)과 `LocalDateTime` 기준이다.
6. **판정과 병합은 다른 규칙이다.** 겹침 판정은 `[start, end)` (맞닿음은 겹침 아님, AS-IS Query와 같음). 병합은 판정으로 나온 겹침 구간들을 표시·비교하려고 맞닿은 것까지 하나로 합치는 것이다. 비교의 단위는 기존 근무에서는 (shiftId, 인계 대상), 신규 추가에서는 newShiftKey다. 시간이 같아도 다른 근무나 다른 인계 대상의 확인으로 통과시키지 않는다.

| 예 (근무 18:00~22:00, 확인한 겹침 18:00~20:00) | 현재 겹침 | 결과 |
|---|---|---|
| 불가능 시간을 17:00~20:00 → 18:00~20:00으로 수정 | 18:00~20:00 | 진행 (관리자가 본 사실 그대로) |
| 18:00~20:00 한 건 → 18:00~19:00, 19:00~20:00 두 건으로 나눔 | 18:00~20:00 (합침) | 진행 |
| 불가능 시간 삭제 | 없음 | 진행 |
| 19:00~21:00으로 수정 | 19:00~21:00 | **다시 확인** (20:00~21:00이 새로 겹침) |
| 다른 날 근무에 새 겹침 | 새 쌍 | **다시 확인** |

Row 단위 부분집합 비교와 달리, 이 규칙은 관리자가 화면에서 본 시간 범위와 같은 기준으로 판단한다.

### 5-4. 미리보기 비교 정보와 확정의 연결 — 1차 기술 계약

**정책 확정 / 기술 후보 구분:** 미리보기 기준은 Decision Log §4-4의 사용자 결정이다. 아래 `previewContext`라는 필드명과 서명 방식은 구현을 위한 후보이며 이미 개발·실험한 결과가 아니다. 해당 Command 착수 시 이 보장을 만족하는 방식을 선택하고 DTO·오류 분기를 확정하면 된다. 문서 공개나 별개 Migration을 위해 새 인프라를 먼저 만들 필요는 없다.

- **원본 범위:** 서버가 미리보기 응답과 동일한 기준 상태에서 공식 근무의 식별자·담당자·상태·시각, DRAFT 식별자·시각·담당 및 삭제 효과, Request/Candidate 식별자·관계·상태와 예상 종료/자격 변경 효과를 정규화한다. 서로 다른 시점의 조회를 섞어 존재한 적 없는 조합을 만들지 않도록 조회 일관성도 검증한다.
- **요청 연결:** API-LV-01이 비교용 `previewContext`를 반환하고 API-LV-02가 이를 그대로 받는 형태를 후보로 한다. 최소한 실행자·workplaceId·퇴사 대상 WorkplaceMember ID·스키마 버전·미리보기 발급 시점·원본 범위를 묶는다. 다른 사용자/근무지/재가입 소속으로 전용할 수 없어야 한다. 인계·취소 선택은 미리보기 후 관리자가 입력하며, 현재 DB에 대한 검증과 분리한다.
- **무결성 권장안:** 읽기 미리보기의 업무 변경0을 유지하기 위해 서버 서명된 self-contained 비교 정보를 우선 검토한다. 이는 로그인을 위한 JWT와 별개다. 서명 키 관리/노출 최소화/크기/기간/다중 인스턴스 호환을 확인한다. 대안으로 서버가 보관한 원본을 찾는 불투명 참조를 사용할 수 있지만 저장소·만료·조회 부작용 범위가 추가되므로 별도 설계한다. 클라이언트의 임의 목록 또는 클라이언트가 다시 계산할 수 있는 무서명 hash만으로 원본을 증명하지 않는다.
- **권한과 현재 사실:** 비교 정보가 유효해도 매 요청에서 인증·관리자 권한·현재 소속·대상 관계와 실제 DB를 다시 조회한다. 비교 정보는 삭제/종료할 Row 목록을 클라이언트가 지정하는 권한이 아니다. 실제 처리 대상은 서버가 현재 상태에서 계산한다.
- **비교 규칙:** 공식 근무 계획은 동일성 검사다. 자동 대상은 정규화한 대상+효과 집합의 부분집합 검사다. 사라진 효과만 있으면 진행 가능, 새 대상/효과 또는 대체된 효과가 있으면 STALE이다. 같은 Candidate가 PENDING→ACCEPTED가 되어 후보자격변경에서 Request종료로 효과가 바뀌는 경우는 STALE이다. 관계/시각 등이 달라 감소인지 판별 불가한 경우에도 STALE이다. 비교를 단순 count·상태Enum 숫자의 대소로 구현하지 않는다.
- **Lock과 원자성:** 현재 영향 발견→후보 전역 순서로 관련 Lock/Guard→잠근 후 최신 상태·새 영향 재조회→미리보기와 비교→우회 불가 충돌/확인 범위 검사→업무 쓰기 순서다. 새로 생긴 Row를 뒤늦게 순서 밖으로 잠그고 계속하지 않는다. 검사 이후 삽입 경합도 다른 Command의 공통 Guard와 함께 막아야 한다. FK·Unique·Hibernate flush를 포함한 실제 MySQL 경합 검증 전 안전성을 확정하지 않는다.
- **오래된 정보/반복:** 유효기간·서명 버전 정책은 구현 착수 때 정한다. 유효기간 내라도 데이터가 달라지면 현재 상태 재검증으로 STALE이 될 수 있다. 만료/유효하지 않은 비교 정보는 새 미리보기를 요구하고 업무 변경0을 보장한다(입력 오류400과 유효한 구형 정보의409 분기는 DTO 설계 때 명시). 중복 확정 성공을 재생하는 멱등성 계약은 아니다. 첫 성공 후 재호출은 이미 종료된 소속의 기존 STATE_CONFLICT 규칙으로 추가 변경을 막는다. 응답 유실/503은 조회로 확인하고 자동 재전송하지 않는다.
- **CONFIRM_REQUIRED 재요청:** 원래 previewContext를 유지하고 확인한 충돌 목록만 추가한다. 자동 처리 대상이 확대됐으면 확인 목록이 있어도 STALE이 우선한다. STALE 후 새 미리보기를 받으면 이전 비교 정보와 충돌 확인은 버리고 현재 계획에 대해 다시 검사한다.
- **검증 범위 구분:** D05-5의 “서명된 동의 증명은 범위 밖”은 불가능 시간 경고에 대한 관리자의 동의 범위를 뜻한다. 여기서 미리보기 원본의 무결성을 검증하는 목적과 다르다. 관리자가 실제로 화면을 읽었다는 사실까지 서버 서명으로 증명한다고 주장하지 않는다. 로그/브라우저 URL에 비교 정보를 남기지 않고 다른 근무지·개인 일정 원본을 포함하지 않는다.

## 7. 동시성 (ML-5로 넘김, 실험 전)

- 불가능 시간 충돌의 다시 계산은 **인계 대상 User Lock 이후**에 한다. 불가능 시간 쓰기는 본인 User Lock을 먼저 잡으므로(G03-IP-01) 둘이 직렬화된다고 **추론**한다.
- 인계 대상이 여러 명이면 User Lock을 **ID 오름차순**으로 잡는다. 이 순서가 ML-5 전역 순서(Workplace → Schedule → Shift → Request → User → Membership 후보)와 맞는지 확인해야 한다.
- 인계 대상 소속을 `FOR SHARE`로 다시 읽는 것만으로 충분한지는 격리 수준(DL-002 READ COMMITTED), 다른 Command의 Lock 방식, 대상 직원 퇴사의 Lock 순서와 함께 실험으로 확인한다.
- 실험 항목: G03-D-21 D21-R1·R2, 여러 대상 인계 vs 대상의 불가능 시간 등록, 여러 대상 인계 vs 대상의 퇴사, 첫 409 이후 상태 변경 0 확인.

## 10. 재검토 조건

- 확인 목록을 동의 증거로 써야 하는 요구(감사 등)가 생기면 서명 Token 또는 서버 확인 상태를 검토한다.
- Publish 개선을 시작할 때 이 형식을 재사용할지 다시 본다.
- ML-5 실험에서 User Lock 직렬화가 성립하지 않으면 §7을 다시 정한다.
- 관리자에게 직원의 불가능 시간을 보여 주는 기능이 생기면 S05-a를 다시 본다.
