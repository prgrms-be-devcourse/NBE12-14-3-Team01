## 1. 왜 지금 정해야 하나

ML-2·ML-3·ML-H2는 퇴사 Command 안에서 일어날 일을 정했다. 이 카드는 **그 Command를 누가, 어떤 조건에서, 어떤 API로 실행하는지**와 **퇴사 후 무엇이 보이는지**를 정한다.

## 2. AS-IS (① `VERIFIED_AS_IS`, 정적 확인)

### 2-1. 퇴사 후 접근 (API별, `31ecaee`)

### 2-2. 그 밖

- 퇴사 Command 없음 (ML-H1). 관리자는 근무지 생성자 1명, 역할 변경 없음 (ML-H2 §2).
- **근무 상세는 CANCELLED 근무를 거부한다** (`IS_CANCELED_SHIFT`, `ShiftService.detail`). ML-2 D27-6("취소된 근무가 직원 화면에서 사라지지 않게")과 맞지 않는다 → §6-1 조회 체계로 해결 (상세 API는 그대로 두고 별도 "빠진 근무" API).

## 3. 사용자 잠정 결정

| ID | 결정 문장 |
|---|---|
| ML-4-1 | 퇴사 Command는 **그 근무지의 현재 MANAGER만** 실행한다. 대상은 **현재 EMPLOYEE 소속**만이다 (ML-H2 H2-9). 서버가 실행자와 대상의 현재 소속·역할을 검사한다 |
| ML-4-2 | 직원이 직접 실행하는 "근무지 나가기"와 앱 안의 퇴사 요청·승인 흐름은 **이번 MVP에서 제외**한다. 직원의 퇴사 의사는 앱 밖에서 관리자에게 전달하고, 관리자가 근무·대타를 정리한 뒤 확정한다 |
| ML-4-3 | **현재 업무 화면은 현재 소속 기준**으로 조회한다: 내 근무지, 내 근무, 근무 상세, 받은·보낸·수락 대타, 알림 |
| ML-4-4 | **보낸 대타 목록(SUB-05)은 현재 소속의 요청만** 보여 준다 (기존 응답 변경, 승인 대상). 과거 Request·Candidate 데이터는 삭제하지 않는다 |
| ML-4-5 | 본인은 **과거 소속 이력**을 볼 수 있다: 근무지 이름, 당시 역할, 가입 시각, 퇴사 시각. 같은 근무지에 여러 번 소속됐다면 기간마다 따로 보인다. **본인 것만** 조회할 수 있다 |
| ML-4-6 | 과거 근무·대타 **상세** 조회는 이번 MVP에서 제외한다 (후속 후보). 영구 금지가 아니라 범위 결정이다 |
| ML-4-7 | 진행 중 공식 근무(`startAt ≤ now < endAt`, 대상이 담당)가 있으면 퇴사를 **거부**하고 그 근무의 종료 시각을 알린다 (이전 사용자 잠정 정책 유지) |
| ML-4-8 | 퇴사는 미리보기와 확정 두 단계다. 확정 시 서버가 Lock 후 최신 상태를 다시 조회하고, 미리보기와 다르면 거부(409 후보)한다. 소속 종료·인계·취소·DRAFT 삭제·대타 정리·배정 이력·(선택) 초대 코드 재발급을 하나의 Transaction으로 처리한다 |

## 4. 보장 범위와 운영 한계

| 보장함 (구현·검증 후) | 운영 한계 (MVP에서 보장하지 않음) |
|---|---|
| 퇴사 확정 후 현재 소속을 요구하는 기능은 거부되거나, 그 소속의 데이터가 보이지 않는다 (§2-1의 빈 곳은 §8에서 수정) | **관리자가 퇴사 처리를 늦게 하면** 그동안 소속·권한·근무 배정이 남는다. 실제 퇴사 시 즉시 처리하는 것은 관리자 책임 (운영 전제) |
| 퇴사자에게는 그 근무지가 내 근무지 목록에서 사라진다 | 직원이 스스로 소속을 끝낼 수 없다 (관리자 미처리·거절 시) |
| 본인의 과거 소속 기간을 확인할 수 있다 | 과거 소속 이력은 **실제 출퇴근·근로 증명이 아니다.** 화면 표현은 "소속 이력" / "참여 이력"으로 한다 (재직증명서 용도 아님) |
| | 근무지 이름·사용자 이름은 **현재 값**을 보여 준다. 당시 이름은 보존하지 않는다 (스냅샷 없음) |
| | 과거 근무·대타 상세 조회 없음 |

| 상황 | 응답 (후보) | 상태 변경 |
|---|---|---|
| 실행자가 현재 관리자가 아님 | 403 `MANAGER_REQUIRED` (기존 WPL-004) | 없음 |
| 대상이 다른 근무지 소속이거나 없음 | 404 / 403 (G03-D-04 노출 정책과 함께) | 없음 |
| 대상이 MANAGER | 409 새 코드 후보 (예: "관리자는 퇴사 처리할 수 없습니다") | 없음 |
| 대상이 이미 종료된 소속 | 409 새 코드 후보 ("이미 종료된 소속입니다"). `leftAt` 그대로 (ML-H1 V2-N-05 결정: 멱등 성공 대신 409) | 없음 |
| 진행 중 근무 있음 | 409 새 코드 후보 + 종료 시각 | 없음 |
| 결정이 미래 공식 근무 전체와 다름 / 담당자가 바뀜 / 상태가 바뀜 | 409 새 코드 후보 ("근무 상태가 바뀌었습니다. 다시 확인해 주세요") | 없음 |
| 인계 대상 검증 실패 (현재 소속 아님, 겹침, 다른 근무지 충돌) | 기존 ErrorCode 재사용 (SFT·SCH 계열) | 없음 |
| 인계 대상의 불가능 시간 겹침 | 경고 후 확인 (ML-2 §8 ①) | 확인 시 진행 |
| 성공 | 200 + 결과 요약 | ML-2·ML-3·ML-H2 전부 |

새 ErrorCode는 3~4개 후보 (WPL 계열). 번호와 Prefix는 G03-D-03과 함께 정한다.

## 6. API 계약 (후보, 경로·이름 미정)

**미리보기** `GET /workplaces/{workplaceId}/members/{memberId}/leave-preview` (현재 관리자만)

| Field | 내용 |
|---|---|
| `member` | 대상 소속 (ID, 이름, 역할, 가입일) |

### 6-1. 직원 조회 체계 (사용자 잠정 결정 2026-10-23)

원칙: **"내가 해야 할 일"과 "나에게서 빠진 일"과 "과거 소속"을 서로 다른 API로 나눈다.** 새로 받은 근무는 미래에 해야 할 일이므로 "내 근무"에 나타나고 알림으로 안내한다. 취소되거나 다른 사람에게 넘어간 근무는 더 이상 내 일이 아니므로 "내 근무"에서 빠지고, 별도 화면에서 확인한다.

| 목적 | API | 데이터 기준 | 계약 |
|---|---|---|---|
| 내가 해야 할 근무 | `GET /schedules/me` (기존) | 현재 소속 + PUBLISHED + SCHEDULED + 현재 담당자 = 나 | **AS-IS 그대로.** 새로 받은 근무(추가·인계·대타 승인)는 여기에 나타남 |
| 근무 상세 | `GET /shifts/{id}` (기존) | 위와 같은 조건 | 현재 소속 확인 추가 (§8 ①). CANCELLED 거부는 **유지** |
| **나에게서 빠진 근무** | **새 API** (예: `GET /schedules/me/removed`) | 현재 소속 기준. ① 담당자가 나인 CANCELLED 근무 (Shift 취소 정보) ② 배정 이력에서 "이전 담당 소속 = 나의 현재 소속"인 인계 근무. **현재 담당자가 나인 근무는 제외** | 새 API (Improvement). 범위는 아래 "빠진 근무 규칙". 근무 시각순. 원래 근무 시각, 근무지, 취소·인계 구분, 사유, 변경 시각 표시 |
| 과거 소속 | 새 API (§6) | 본인의 종료된 소속 | ML-4-5 |
| 관리자 근무표 | 기존 | 근무표 전체 + 상태·취소·인계 정보 | 응답 Field 추가 |
| 변경 알림 | 알림 목록 (기존) | 새 Type: 배정됨 / 취소됨 / 다른 직원에게 넘어감 | 보조 수단 (유실 가능, G03-D-22) |

**빠진 근무 규칙 (2026-10-23 보완):**
- **정의:** 내 현재 소속에 공식 배정된 적이 있으나, 지금은 그 근무가 취소됐거나 담당자가 다른 소속인 근무.
- **조회 기간 (사용자 잠정 결정 2026-10-23):** 원래 근무 시작 시각 기준 **미래 + 최근 7일**. 시작 시각이 지나자마자 목록에서 사라지면 알림을 놓친 직원이 뒤늦게 확인할 수 없기 때문. **조회 범위일 뿐 보존 기간이 아니다.** 7일보다 오래된 취소 정보·배정 이력도 지우지 않는다.
- **보여 줄 사건:** 각 소속에게 **자기 배정이 끝난 그때의 사건**을 보여 준다. A→B 인계 후 B 담당일 때 취소되면 A는 "인계됨", B는 "취소됨". A에게 B 시점의 취소를 새로 보여 주지 않는다. A→B→C면 A·B 모두 "인계됨".
- **같은 근무는 소속마다 한 줄:** A→B→A 후 취소되면 A에게는 마지막 사건인 "취소됨" 한 줄만 (예전 "인계됨"과 중복 표시하지 않음). A→B→A로 지금 A 담당이면 A에게는 표시하지 않고, B에게는 "인계됨".
- **대타 승인과의 경계:** 대타 승인으로 넘어간 근무는 "빠진 근무"에 넣지 않고 보낸 대타 목록(SUB-05, APPROVED)에서 본다. 두 화면에 같은 근무가 중복으로 나오지 않는다.
- **새 배정**은 "내 근무" + 알림으로 안내한다. 별도 "새 배정 내역" API는 만들지 않는다.
- **데이터 출처와 조회 규칙 (소속 M 기준):**
  - 후보 근무 = ① `shift.member = M`이고 CANCELLED인 근무 ∪ ② 배정 이력에서 `이전 담당 = M`인 근무
  - 근무마다 한 줄: `shift.member = M`이면 → "취소됨" (CANCELLED는 끝 상태라 취소 뒤 담당자가 바뀌지 않으므로 **`shift.member`가 곧 취소 당시 담당자**). `shift.member ≠ M`이면 → M이 이전 담당인 이력 중 **가장 마지막 Row**로 "인계됨"
  - `shift.member = M`이고 SCHEDULED면 제외 (지금 내 근무)
  - Field 출처: 취소 = Shift의 취소 사유·시각·행위자 (D-26 R1) / 인계 = 배정 이력의 사유·시각·행위자·새 담당 (D27-4)
  - 예: A→B→A→취소 → A: 취소됨 1줄, B: 인계됨 1줄. A→B→C → A: 인계됨, B: 인계됨
  - 이 규칙은 **조회 Query Test로 확인**한다 (V2-N-39)

- **소속 기간 구분:** 배정 이력은 User가 아니라 **당시 WorkplaceMember ID**로 저장한다 (ML-2 D27-4). 그래서 재가입 후 이전 기간의 기록이 섞이지 않는다.
- **대타 승인으로 넘어간 근무**는 "빠진 근무"에 넣지 않는다. 요청자 본인이 요청한 일이고, 보낸 대타 목록(SUB-05)에 APPROVED로 보인다 (배정 이력에 대타 승인을 쓰지 않는 ML-2 §8 ④와 일치).
- **두 출처를 합치는 비용:** 취소(Shift Row)와 인계(배정 이력)를 합쳐 정렬한다. "시작 전"으로 범위를 제한하면 건수가 작아 페이지네이션 없이 Service에서 합칠 수 있다 (구현 시 확인).
- **확인 완료 상태(읽음 표시)**는 이번 MVP에서 제공하지 않는다.

이전 결정과의 차이: ML-2 §8 "내 근무가 CANCELLED도 반환"과 ML-4 §8 ② "취소 근무 상세 허용"을 이 체계로 **대체**한다. 기존 두 API의 계약이 그대로 남아 Migration 기준(현재 동작 보존)과 충돌이 줄어든다.

## 7. 퇴사 후 Frontend

- 퇴사자가 그 근무지 화면에 있다가 요청이 거부되면(WPL-003 등) 근무지 목록으로 이동하고 안내한다.
- 관리자 화면: 구성원 목록에서 퇴사 버튼은 EMPLOYEE에만 표시 (서버 검사가 기준). 미리보기 → 근무별 선택 → 확정 → 결과 요약.
- 과거 소속 이력은 **마이페이지의 "내 소속 이력"**에 둔다 (사용자 결정 2026-10-23). "내 근무" 화면의 탭에는 "예정 근무"와 "빠진 근무"만 둔다.
